## 0. 先读这一节：三个比方

**比方一：端口映射 = 在你家墙上开一扇没有锁的门。**
你在路由器上做端口映射（port forwarding），本质是告诉全世界：「我家这个地址的这个门，谁都能来敲。」门后面站着的是你的 ESP32。ESP32 上跑的是一个几百 KB 的小程序，它没有操作系统、没有杀毒软件、没有自动更新。一旦有人发现这扇门，他就可以一直敲、一直试、一直找漏洞。

**比方二：MQTT 出站 = 你的设备主动给「传达室」打电话。**
MQTT 方案里，ESP32 不开放任何门，而是自己主动拨号连到云端的一台服务器（broker，中文叫「消息代理」，你可以理解成一个传达室）。设备连出去之后，就一直保持这条线。手机想发指令，就把话交给传达室，传达室再转给设备。**外面的人根本不知道你家在哪**，因为他看不到门——门根本不存在。

**比方三：TLS = 给这条电话线套一根防窃听的管子。**
TLS（Transport Layer Security，传输层安全协议）就是 HTTPS 里那个「S」。它保证两件事：
1. **加密**：中间人偷听也听不懂。
2. **身份验证**：电话那头确实是「真的传达室」，不是冒充的。

这三条，就是整个方案的地基。

### 1.2 数据流（一次「按一下电源键」发生了什么）

1. 手机 App 连上 EMQX（TLS），向主题 `psw/<device_id>/cmd` 发布一条 JSON：`{"cmd":"press","nonce":"...","ts":...}`。
2. broker 检查认证与 ACL：这个账号有没有权限往这个主题发？没有就直接丢掉。
3. broker 把消息推给订阅了该主题的客户端 —— 只有你的 ESP32。
4. ESP32 收到消息，先做本地校验（nonce 是否用过、时间戳是否在窗口内、topic 是否**恰好**是自己那一个）。
5. 校验通过 → GPIO5 拉高 **300 毫秒** → 光耦内 LED 发光 → 光敏三极管导通 → PWR_SW 两脚被短暂短接 → 主板认为「有人按了电源键」。
6. GPIO5 拉低 → 光耦关断 → 按钮「松开」。
7. ESP32 向 `psw/<device_id>/ack` 发布 `{"cmd":"press","result":"ok","duration_ms":300}`。

**关键点一：整个过程 ESP32 从来没有「被连接」，它只是自己连出去然后收消息。**

**关键点二：ESP32 和 PC 之间在电气上是完全断开的。** 唯一穿过边界的是光。

## 2. 为什么不用端口映射

### 2.1 对比表

| 维度 | 端口映射（Port Forwarding） | MQTT 出站（本方案） |
|---|---|---|
| **攻击面** | ESP32 必须监听一个公网端口，全世界都能扫到。Shodan 之类的扫描器几分钟内就会发现你 | ESP32 不监听任何端口，公网上找不到它。攻击者连「目标存在」都不知道 |
| **认证强度** | 通常靠一个 HTTP 密码或 token。裸 HTTP 明文传输，抓包即得 | 强制 TLS。可叠加用户名/密码 + 客户端证书 |
| **DoS（拒绝服务）** | 攻击者只要疯狂发连接请求，ESP32 那点内存瞬间被耗尽，直接死机。路由器层面很难限流 | ESP32 只跟 broker 建一条连接。攻击者要打只能打云 broker，而专业 broker 有连接数限制、限流、黑名单 |
| **固件提取** | 攻击者一旦攻破，可以直接 dump flash，拿到 Wi-Fi 密码和所有密钥 | 同样能 dump flash，但**拿不到任何入站通道**，也拿不到 broker 的私钥 |
| **漏洞影响面** | 你的每个设备都是一台「公网服务器」，要各自打补丁 | 漏洞集中在 broker 一侧，EMQX 由厂商维护 |
| **可审计性** | 基本没有日志 | broker 天然有连接日志、发布/订阅日志、ACL 拒绝日志 |
| **家用宽带限制** | 很多运营商是 CGNAT（大内网），根本没有公网 IP，端口映射根本做不了 | 不依赖公网 IP，出站连接永远可用 |
| **证书/密钥轮换** | 无统一机制 | broker 侧统一管理，ACL 一改全局生效 |

### 2.2 一句话总结

> **端口映射是把门开向世界；MQTT 出站是把设备变成世界的一个「客户」。**
> 客户只能主动打电话，不能被人打进来。

### 2.3 那端口映射完全不能用吗？

可以用，但必须满足**全部**以下条件，本项目的条件显然不满足：
- 有静态公网 IP，且不是 CGNAT
- 设备端跑得动一个成熟的反向代理（如 WireGuard 隧道），而不是裸 HTTP
- 你能做端口敲门（port knocking）或 IP 白名单
- 你能 7×24 盯日志、及时打补丁

## 3. TLS 证书方案

### 3.1 先讲清楚三个名词

| 名词 | 通俗解释 |
|---|---|
| **CA**（Certificate Authority，证书颁发机构） | 相当于「派出所」。它给设备发身份证，并且用自己的公章（根证书）担保这张身份证是真的 |
| **服务器证书** | broker 的身份证。ESP32 要验证「我连的确实是真 broker」 |
| **客户端证书** | 设备的身份证。broker 要验证「连我的确实是我的设备」。这叫**双向认证（mTLS）** |

### 3.2 本项目的实际情况：broker 是 EMQX Cloud Serverless

这改变了证书策略：

- 你**不需要**自己搭 CA、不需要自己签 broker 证书 —— EMQX 已经做好了，它用的是公共 CA（浏览器/系统信任的那种）。
- 你**需要**做的是：拿到 EMQX 部署的**根 CA 证书**，内嵌进 ESP32 固件，让 ESP32 能验证「我连的确实是 EMQX，不是冒充的」。

**从哪里拿？** EMQX Cloud 控制台里通常有「下载 CA 证书」或「连接信息」页面，会给你一个根证书 PEM 文件。

**两种内嵌方式，选哪个？**

| 方式 | 大小 | 说明 |
|---|---|---|
| 内嵌 EMQX 给的那一个根 CA（PEM 文本） | 约 1~2 KB | ✅ **推荐**。精确、省 flash |
| 用 ESP-IDF 内置的公共 CA bundle（`esp_crt_bundle_attach`） | 约 64 KB | 能用，但为了一个 broker 塞 64KB 证书进 4MB flash，浪费 |

**你的设备只有一台、broker 只有一个，所以内嵌那一个精确的根 CA 是最优解。**

### 3.3 客户端证书（mTLS）—— 在 Serverless 上大概率用不了

> ⚠️ **需要你去 EMQX 控制台确认。**
>
> 据我所知，EMQX Cloud 的 **Serverless（共享版）很可能不支持客户端证书认证** —— mTLS 通常需要「独享部署」，而独享部署是要付费的。
>
> 如果确实不支持，那就走这条路：**每设备独立的长随机用户名/密码 + 严格 ACL + 设备端 topic 自校验**（见 4.5）。这个组合对单设备家用场景是够用的。

### 3.4 broker 服务器证书怎么校验（ESP-IDF 示意）

```c
extern const char emqx_root_ca_pem[] asm("_binary_emqx_ca_pem_start");

esp_mqtt_client_config_t cfg = {
    .broker.address.uri = "mqtts://<你的EMQX接入地址>:8883",
    .broker.verification.certificate = emqx_root_ca_pem,
    .credentials.client_id = DEVICE_ID,
    .credentials.username  = DEVICE_USER,
    .credentials.authentication.password = REDACTED_DEVICE_PASS,
};
```

把 `emqx_ca.pem` 放进 `main/` 目录，并在 `main/CMakeLists.txt` 里用 `EMBED_FILES` 嵌进去：

```cmake
idf_component_register(SRCS "main.c"
                    INCLUDE_DIRS "."
                    EMBED_FILES "emqx_ca.pem")
```

**规则：**
- 必须开启主机名校验（`esp-tls` 默认就开着，别关）。
- 证书要和连接地址匹配 —— 如果你连的是 IP 而不是域名，主机名校验会失败。**所以一定要用 EMQX 给你的域名连接。**

### 3.5 ⚠️ 明确警告：绝对不要跳过证书校验

ESP-IDF 里有一些「图省事的开关」，**在任何非本机实验的环境下都不许用**：

| 危险选项 | 后果 |
|---|---|
| `skip_cert_common_name_check = true` | 不校验主机名 → 中间人可以拿**任何**合法证书冒充你的 broker |
| `.broker.verification.certificate = NULL` 且不挂 bundle | 等于不校验服务器身份 → 中间人攻击完全成立 |
| 使用「自签名证书 + 不校验」组合 | 加密还在，但**身份验证没了**。你以为在跟 broker 说话，其实在跟攻击者说话 |

> **记住一句话：TLS 没有身份验证，就只是「加了密的中间人通信」。**
> 加密解决「被偷听」，身份验证解决「被冒充」。两个都要。

**这里有个真实的诱惑：** EMQX Serverless 的域名有时用 IP 直连或证书 CN 不匹配，很多人为了让它连上就把校验关了。**这是本方案最容易被自己破坏的一环。** 正确做法是去找 EMQX 文档里给出的「推荐连接域名」，而不是关校验。

### 3.6 密钥管理红线

- MQTT 密码**永远不进 Git**（`.gitignore` 里加 `secrets/`、`*.key`、`*.pem`、`sdkconfig`）。
- 建议用一个 `secrets.h`（在 `.gitignore` 里）存用户名密码，仓库里只放 `secrets.h.example`。
- 如果以后切自建 CA，CA 私钥离线保存（U 盘 / 密码管理器 / 纸），**绝不放在 broker 服务器上**。

## 4. MQTT 主题与鉴权设计

### 4.1 Topic 命名

```
psw/<device_id>/cmd       ← 手机 → 设备：下发指令      （设备只订阅这一个）
psw/<device_id>/state     ← 设备 → 手机：开关机状态    （设备发布，retained，二期）
psw/<device_id>/status    ← 设备 → 手机：在线状态/LWT  （设备发布，retained）
psw/<device_id>/ack       ← 设备 → 手机：指令执行确认  （设备发布）
```

`<device_id>` 建议用 ESP32-C3 的 MAC 派生（例如 `psw-3c84f7`），保证全球唯一且不含敏感信息。

**规则：**
- 设备**绝不订阅** `psw/+/cmd`、`psw/#` 这类通配符。
- 设备**绝不发布**到别人的前缀。
- 手机 App 只订阅 `psw/<device_id>/state` 和 `/status`，只发布 `/cmd`。

### 4.2 指令格式（JSON）

```json
{
  "cmd": "press",
  "nonce": "7f3a9c21",
  "ts": 1760600000,
  "ttl": 30
}
```

| 字段 | 作用 |
|---|---|
| `cmd` | `press`（按一下，300ms） / `press_long`（长按，用于强制关机，需二次确认） |
| `nonce` | 一次性随机数。设备记住最近 N 个 nonce，重复的直接丢弃 |
| `ts` | Unix 时间戳（秒）。设备校验 `|now - ts| <= ttl` |
| `ttl` | 允许的时间窗口（秒），默认 30 |

**为什么只有 `press` 没有 `on`/`off`？**

这是本项目最重要的一个设计认知转变：

> **你的「执行器」是一个瞬时按钮，不是一盏开关。**
>
> 真实的机箱电源键，你按一下 = 状态翻转（开着的关机，关着的开机）。你**无法**通过这个按钮「强制打开」或「强制关闭」—— 你只能「按一下」。
>
> 所以指令语义必须是 `press`，而不是 `on`/`off`。如果你把 App 上的按钮做成「开机 / 关机」，那是**假承诺**，用户会误以为它是幂等的。

**这个问题的正式解法见 5.9（第二个光耦做状态回读）。在二期做完之前，App 上的按钮必须老老实实叫「按一下电源键」。**

### 4.3 防重放（Replay Attack）

**攻击场景：** 攻击者抓到了你 10 秒前发的一条 `{"cmd":"press"}` 报文，原样再发一次。如果设备不做校验，电脑就被多按了一下 —— 可能正好把它关掉。

**防御：**
- `ts + ttl` 限制「只在 30 秒内有效」。
- `nonce` 保证「同一条报文只能用一次」。

**MQTT QoS 1 会重复投递。** QoS 1 的语义是「至少一次」，broker 在网络抖动时可能把同一条消息发两遍。**nonce 去重不只是防攻击者，也是在防 broker 自己。** 这条很重要：没有 nonce，你自己的网络抖动就会让电脑被多按一下。

**ESP32 的时钟问题：** C3 没有电池供电的 RTC，重启后时间归零。方案：
- 启动后先用 SNTP（`esp_sntp`）同步时间。
- **在同步成功之前，拒绝执行任何指令**（或降级为仅允许本地物理按钮）。
- 这一点不能省，否则时间校验形同虚设。

建议用 **QoS 1** 而不是 QoS 0（QoS 0 可能丢指令，用户按了没反应，体验很差）。

### 4.4 Broker 侧 ACL

理想情况（自建 Mosquitto / EMQX 独享版）：

```
user psw-3c84f7
topic read  psw/3c84f7/cmd
topic write psw/3c84f7/state
topic write psw/3c84f7/status
topic write psw/3c84f7/ack

user app-user01
topic write psw/3c84f7/cmd
topic read  psw/3c84f7/state
topic read  psw/3c84f7/status
```

**每条规则都是白名单。没有匹配规则 = 拒绝。**

> ⚠️ **EMQX Cloud Serverless 的 ACL 能力需要你在控制台确认。**
>
> Serverless 共享版为了简化，可能只提供「用户名密码认证」，而不开放细粒度的 topic ACL 配置。**如果确实不能配 ACL，那么「每设备独立前缀」的安全性就依赖于「每设备独立密码」这一层。**
>
> **对策（必做）：在 ESP32 固件里自己做 topic 校验。** 收到消息后，检查 topic 字符串是否**逐字节等于** `psw/<自己的device_id>/cmd`。不等于就丢弃并记一条日志。
>
> 这个检查只有几行代码，但它把「broker 配置不当」这个风险从架构里消掉了 —— 这叫**纵深防御**：不假设上游一定做对了。

### 4.5 用户名密码 vs 客户端证书，用哪个？

| 方案 | 安全性 | 复杂度 | 本项目建议 |
|---|---|---|---|
| 用户名 + 密码 | 中。密码存在 flash 里，被 dump 就泄漏 | 低 | ✅ **MVP 用这个**（EMQX Serverless 唯一可行项） |
| 客户端证书（mTLS） | 高。私钥不可暴力破解；可单独吊销 | 中高 | ❌ Serverless 大概率不支持；二期若要上，需迁独享部署 |

**结论：**
- **MVP**：TLS + 每设备独立的长随机密码（建议 32 位）+ 设备端 topic 自校验。
- **绝对不要**所有设备共用一个密码。对单设备项目来说这不是问题，但要记住这个原则。
- 密码生成示例（本地执行，不联网）：`openssl rand -base64 32`

## 5. 817D 光耦驱动设计（核心章节）

### 5.0 Wi-Fi 频段问题（已解决 ✅）

**ESP32-C3 只支持 2.4GHz Wi-Fi，不支持 5GHz。**

这里曾经有个坑：路由器广播的是 `LEDE-5G`，带 `5G` 后缀，是 5GHz 专用网络 —— ESP32 扫不到它、也连不上，而且失败方式很隐蔽（`esp_wifi` 只报告「找不到该 SSID」，`WIFI_REASON_NO_AP_FOUND`），新手很容易误以为是密码错或驱动问题，然后卡半天。

**已确认解决：** 你的路由器上 2.4GHz 的 SSID 就叫 **`LEDE`**（不带 `-5G`）。

配置时用：

```c
#define WIFI_SSID  "LEDE"                 // 2.4GHz，不是 LEDE-5G
#define WIFI_PASS  "<你的Wi-Fi密码>"        // 真实密码放 secrets.h，见文件开头警告
```

**顺便：** 你的路由器是 OpenWrt/LEDE —— 好消息，第 8 章的访客网络/VLAN 隔离它天生就支持，不用换硬件。

#### ⚠️ 关于 Wi-Fi 密码本身

你现在的 Wi-Fi 密码比较短。对家用来说它不算致命，但考虑到：

- 这个网络里即将接入一个「能控制你电脑电源」的设备；
- 密码一旦泄漏，攻击者不需要攻破 ESP32，**他直接连上你的 Wi-Fi 就能发 MQTT 指令**。

**建议把 Wi-Fi 密码改成更长的随机串**（12 位以上，含大小写+数字）。这是成本最低、收益最直接的一步加固，比后面任何一项都划算。

**改密码前请确认：** 家里其他设备（手机、电视、摄像头…）记得重新连。如果嫌麻烦，至少别把这个密码写进任何会进 Git 的文件。

### 5.1 你的方案为什么是对的（先给结论）

**不用继电器、只用光耦，是这道题的正确答案。** 理由：

1. **主板 PWR_SW 是低压信号（约 3.3V，微安级电流），不是市电。** 继电器是「用低压控制大电流负载」的器件，这里根本没有大电流负载 —— 你的「负载」是两个排针之间的一个逻辑电平。用继电器是杀鸡用牛刀，还引入了线圈驱动、反向电动势、体积、噪声一堆麻烦。
2. **光耦在这里同时干了三件事**：传递信号、电气隔离、以及最关键的 —— 它**变成了一个「干接点」**，对主板来说和一个真实的按键开关没有区别。
3. **隔离是这个应用的刚需**，不是可选项。理由见 5.2。

所以：**你的选型不用改，直接往下做。**

### 5.2 为什么必须隔离（不隔离会发生什么）

有四个具体的坏结果：

| # | 问题 | 具体后果 |
|---|---|---|
| 1 | **背灌（back-powering）** | 不隔离时，PC 待机时 PWR_SW 上的 3.3V 会通过你的电路倒灌进 ESP32 的 GPIO。ESP32 会通过它的 ESD 保护二极管给整个 3.3V 轨充电，芯片进入一种「半死不活」的僵尸状态 |
| 2 | **地环路** | ESP32 的地和 PC 的地连在一起，如果 ESP32 还插着 USB，就形成了一个大环路 —— 天线效应，容易受干扰、容易复位 |
| 3 | **参考点丢失** | PC 拔掉电源线后，它那边的「地」和「3.3V」参考都消失了，你的 GPIO 会处于一个不确定的电位 |
| 4 | **噪音注入** | ESP32 的开关噪声直接进主板待机电路，可能导致主板误判按键、甚至干扰开机自检 |

**有了光耦，这四条全部消失。** 唯一穿过边界的是光。

### 5.3 817D 引脚确认（动手前必做）

> ⚠️ **不同厂家、不同型号的 4 脚光耦，引脚定义不保证一致。**

PC817 系列（含 PC817D、EL817、LTV-817）的标准引脚是：

```
      ┌─────┐
  1 A │●    │ 4 C
  2 K │     │ 3 E
      └─────┘
```

| 脚 | 名称 | 含义 |
|---|---|---|
| 1 | A（Anode，阳极） | 内部 LED 正极 |
| 2 | K（Cathode，阴极） | 内部 LED 负极 |
| 3 | E（Emitter，发射极） | 输出侧光敏三极管发射极 |
| 4 | C（Collector，集电极） | 输出侧光敏三极管集电极 |

**怎么验证（万用表二极管档）：**
- 找到正向压降约 **1.0~1.3V** 的两个脚 —— 那就是 1（A，红表笔）和 2（K，黑表笔）。反接应该不通。
- 剩下两个脚就是输出侧。用二极管档测它们，两边都不通（因为是三极管，不是二极管）。

**如果测出来不对，别硬接，把丝印告诉我。**

### 5.4 典型电路

```
╔══════════════ ESP32 侧：独立 USB 充电头供电，独立 GND ═══════════════╗
║                                                                     ║
║    GPIO5 ──[ R1  220Ω ]──┬──►|──→ 817D pin1 (阳极 A)                ║
║                          │  LED                                    ║
║    GPIO5 ──[ R2   10kΩ ]─┤                                         ║
║                          │                                         ║
║                         GND ────→ 817D pin2 (阴极 K)                ║
║                                                                     ║
║    每个 GPIO 到光耦之间只有一个电阻 R1，没有别的元件。                 ║
╚═════════════════════════════╤═══════════════════════════════════════╝
                              │
     ┌────────────────────────┴────────────────────────┐
     │   隔离边界：817D 内部，≈ 5 kVrms                  │
     │   ESP32 的地和 PC 的地在这里被彻底切断            │
     │   （两边唯一的联系是光）                          │
     └────────────────────────┬────────────────────────┘
                              │
╔═════════════════════════════╧═══════════════════════════════════════╗
║              PC 主板侧：与 ESP32 不共地                              ║
║                                                                     ║
║    817D pin4 (集电极 C) ────→ 主板 PWR_SW 信号脚（约 3.3V）          ║
║    817D pin3 (发射极 E) ────→ 主板 PWR_SW 地脚  （0V）              ║
║                                                                     ║
║    机箱物理电源键 ────── 与上面并联 ──────┘                          ║
║    （物理按键照常能用，两条路互不干扰）                                ║
║                                                                     ║
╚═════════════════════════════════════════════════════════════════════╝
```

**这就是全部电路。** 没有继电器、没有驱动三极管、没有续流二极管。

**一个容易被忽略的性质：** 你的电路和机箱物理电源键是**并联**的。这意味着：
- 你自己坐在电脑前，照样能按物理键；
- 光耦坏了，物理键还能用（冗余）；
- 这正是一个「模拟按键」方案该有的样子。

### 5.5 主板 PWR_SW 到底是什么（先搞懂再接线）

| 特征 | 说明 |
|---|---|
| **它是按钮，不是开关** | 你按住它才有连接，松手就断开。所以你不能「保持打开」 |
| **两个脚** | 一个是被主板内部电阻上拉到约 3.3V（或 5VSB）的**信号脚**；另一个通常是**地脚**。你量到的 3.3V 就是那个上拉 |
| **按一下** | 短接约 100~500ms = 一次按键 = 开机或关机（**翻转**） |
| **按住 4 秒** | 短接 ≥4 秒 = **强制断电**（硬关机，等同于拔电源，有数据丢失风险） |
| **待机可用** | 只要 PC 电源线插着、电源开关打开，待机 5VSB 就在，按键电路就有效 —— 所以你可以远程开机 |

> **验证方法（强烈建议动手做）：** 拔掉机箱前面板的电源键排线，拿一把绝缘柄螺丝刀，轻轻短接 PWR_SW 两个脚一下。电脑应该开/关机。这一步能确认「排针位置对不对」「极性怎么接」，而且完全不涉及你的电路。
>
> ⚠️ 用**绝缘柄**螺丝刀，手不要碰到金属部分，另一只手不要碰机箱金属。

### 5.6 电阻怎么算（讲人话）

**R1（限流电阻）：**

```
ESP32 GPIO 输出 3.3V
817D 内部 LED 正向压降约 1.2V
希望流过 LED 约 10mA（ESP32 单脚推荐上限 20mA，取一半更稳）

R1 = (3.3 - 1.2) / 0.010 = 210 Ω  →  取标准值 220Ω
实际电流 ≈ (3.3 - 1.2) / 220 ≈ 9.5 mA
```

**为什么 10mA 就够了？**
主板的上拉电阻通常是 10kΩ 左右。光耦导通时，需要的电流只有 `3.3V / 10kΩ = 0.33mA`。而 817D 的电流传输比（CTR）最差也有 50%，9.5mA 输入至少能拉动 4.7mA 输出 —— **余量 14 倍**。

所以不要为了「更保险」而把 R1 降到 100Ω 以下。那样只会白白增加 ESP32 的发热和功耗，对可靠性没有任何帮助。

**R2（下拉电阻）：**

10kΩ，从 GPIO5 接到 ESP32 的 GND。作用是：ESP32 复位期间 GPIO 是悬空的（高阻态），下拉电阻确保它被牢牢拉在 0V，不会被周围的电磁噪声感应出电压而误触发。

### 5.7 上电默认安全态：这次是天生安全的 ✅

好消息：**你这个电路的安全态是「免费」得到的，不需要费劲设计。**

原因：

1. ESP32-C3 复位后，GPIO 默认是**高阻态（Hi-Z）**—— 相当于断路。
2. 断路 → 没有电流流过 R1 → 光耦内 LED 不发光 → 光敏三极管截止 → PWR_SW 两脚断开 → **PC 完全不受影响**。
3. R2 下拉是双保险。

**这就是为什么「用光耦」比「用继电器」在本项目里更安全：** 继电器模块如果是低电平触发，上电瞬间可能误吸合；而光耦是「不给电流就什么也不做」，天生 fail-safe。

**故障模式分析（这一段请认真读）：**

| 故障 | 结果 |
|---|---|
| ESP32 掉电 | GPIO 变高阻 → 光耦断开 → PC 不受影响 |
| ESP32 复位 | 同上 |
| 程序崩溃并重启 | 同上（复位过程 GPIO 高阻） |
| 程序死锁、GPIO **卡在高电平** | PWR_SW 被持续短接 → 4 秒后主板**强制断电** |

**注意最后一行：最坏结果是「电脑被强制关机」，而不是「电脑意外开机」。** 这是一个相对安全的失败方向 —— 不会出现「半夜电脑自己开机」这种恐怖场景。

**但也正因为这一行，Task WDT（看门狗）在本项目里不是可选项，而是安全相关项。** 没有看门狗，一次死锁就可能让电脑被硬关机、丢失未保存的工作。

**软件上的额外保证：**
- 脉冲生成必须在一个**独立任务**里做，并且这个任务要在看门狗的监控下。
- 脉冲函数必须是「拉高 → `vTaskDelay(300ms)` → 拉低」的直线代码，中间不能有阻塞等待网络、等待锁之类的操作。
- 绝对不要在 MQTT 回调（事件循环）里直接拉 GPIO —— 那样一旦回调被阻塞，脉冲宽度就失控了。用队列把指令传给脉冲任务。

### 5.8 引脚选择（针对你的 ESP32-C3 PRO Mini）

你这块板子的引脚分布：左侧 A0~A4（= GPIO0~GPIO4），右侧 GPIO5、6、7、8、9、10、20、21。

#### ❌ 绝对不要用的

| 引脚 | 板子标注 | 为什么不能用 |
|---|---|---|
| **GPIO2** | A2 | **Strapping 引脚**。上电瞬间芯片会读它来决定启动模式，外部电路会影响读取 |
| **GPIO8** | SDA | **Strapping 引脚**，且板子把它当 I2C 用，可能带了外部上拉 |
| **GPIO9** | SCL | **Strapping 引脚**。低电平 = 进入下载模式。接负载可能导致无法启动 |
| **GPIO20** | RX | UART0 接收，是默认串口控制台。用了就没日志可看 |
| **GPIO21** | TX | 同上 |

> **Strapping 引脚是什么？** 打个比方：芯片上电那一瞬间，硬件会飞快地看一眼这几个引脚的高低电平，据此决定「我是正常启动，还是进入下载模式」。这个「看一眼」发生在你的代码运行之前，你控制不了。所以这几个脚必须留空，不能接任何会拉偏它们的东西。

#### ✅ 推荐

| 用途 | 引脚 | 板子标注 | 说明 |
|---|---|---|---|
| **输出：驱动光耦** | **GPIO5** | MISO | 不用 SPI 就完全空闲，首选 |
| **输入：读 PC 电源状态（二期）** | **GPIO6** | MOSI | 同样空闲 |
| 备选输出 | GPIO3 / GPIO4 | A3 / A4 | ADC 脚，做数字 IO 也完全可以 |
| 备选输出 | GPIO7 / GPIO10 | SS / GPIO10 | 可用 |

**所以：MVP 阶段就用 GPIO5。**

### 5.9 二期强烈建议：加第二个光耦，读出 PC 真实状态

#### 5.9.0 先说人话：这到底是个什么东西

**一句话版本：** 你家客厅的灯，开关在墙上。你在卧室**能按这个开关**，但**看不见灯亮没亮**。第二个光耦就是给这盏灯装一个「从卧室也能看见的指示灯」。

**再换个更贴近你的说法：** 你打电话让室友帮你按一下电脑电源键。问题是 —— 室友**不知道电脑原来是开着还是关着**，你也不知道。你说「帮我开一下」，他按下去，如果电脑本来就开着，这一按就把它**关掉了**。第二个光耦的作用，就是让室友能看见电脑屏幕，并且告诉你「它现在是开的」。

**先设想一个场景。**

你家客厅有盏灯，开关在墙上。现在你人在卧室，想远程把客厅灯打开，但你**看不见客厅**。你只能做一件事：**伸手去按那个开关**。

问题来了 —— 按一下是「切换」，不是「打开」：

- 如果客厅灯现在是**关着**的 → 你按一下 → 灯亮了 ✅ 你想要的
- 如果客厅灯现在是**开着**的 → 你按一下 → 灯灭了 ❌ 正好相反

**而你根本不知道现在是哪种情况**，因为你看不见。

这就是你现在这套系统的处境：**你只能「按一下」电脑的电源键，但你看不见电脑现在是开着还是关着。**

---

**那怎么解决？装一个「能看见」的东西。**

比方说：你在客厅装了一个**小灯**，连到那盏灯的电线上。

- 客厅灯亮着 → 小灯也亮 → 你从卧室能看到「哦，客厅灯是开着的」
- 客厅灯关着 → 小灯不亮 → 你知道「客厅灯是关着的」

现在你就能做**正确的决定**了：

| 你想做的事 | 小灯的状态 | 你的动作 |
|---|---|---|
| 想开灯 | 小灯亮着（已经开了） | **什么都不做** ✅ |
| 想开灯 | 小灯不亮（关着） | 按一下 |
| 想关灯 | 小灯亮着（开着） | 按一下 |
| 想关灯 | 小灯不亮（已经关了） | **什么都不做** ✅ |

**这就是「第二个光耦」的全部意义：给电脑装一个「小灯」，让 ESP32 能看见电脑的真实开关机状态。**

---

**具体到电路上，「小灯」是什么？**

电脑机箱里有一根 **SATA 电源线**（就是给硬盘供电的那根），上面有红线和黑线：

- **红线 = 5V**
- **黑线 = 地（GND）**

关键性质：**电脑开机时，这根红线上才有 5V；电脑关机时，这根线是没电的。**

（顺便解释一个容易混的点：电脑关机但插着电源时，主板上确实还有一路「待机 5V」（叫 5VSB），电源键就是靠它工作的 —— 但**这路待机 5V 不会送到 SATA 线上**。所以 SATA 红线是「开机才有电」，正好可以当「电脑开着吗」的指示灯。）

所以接法是：

- SATA **红线（5V）** → 电阻 → 第二个光耦的输入侧 LED
- SATA **黑线（GND）** → 光耦输入侧 LED 的另一端
- 光耦输出侧 → ESP32 的一个 GPIO（比如 GPIO6），配一个 10kΩ 上拉电阻

ESP32 读这个脚：

- 读到**高电平** → 光耦没导通 → SATA 没电 → **电脑是关着的**
- 读到**低电平** → 光耦导通了 → SATA 有电 → **电脑是开着的**

**注意：这仍然保持了隔离。** 因为信号还是通过「光」传过来的，SATA 那侧和 ESP32 这侧的地依然不连。

---

**为什么选 SATA 线，不选主板上的 PWR_LED 排针？**

主板前面板确实有个 `PWR_LED` 排针（就是机箱上那个电源指示灯）。但它有两个坑：

1. **正负极各家主板不一样**，接反了不亮，容易搞错。
2. 主板已经串了限流电阻，你再加一个电阻可能导致灯太暗，不加又可能过流。

而 **SATA 电源线是国标统一的**：红色永远是 5V，黑色永远是 GND，**不存在接反的可能**。你只需要一根几块钱的 SATA 电源分线器（一分二），把其中一个头拿来接光耦就行。

---

**加了它，你能得到什么？**

| 好处 | 具体是什么 |
|---|---|
| **1. 不再「盲按」** | 这是最重要的。App 上「开机」「关机」变成**幂等**操作 —— 已经开着的，点「开机」不会误把它关掉 |
| **2. App 能显示真实状态** | 打开 App 就能看到「电脑：开机中 / 已关机」，而不是只能看 ESP32 在不在线 |
| **3. 能发现「按了没反应」** | 发了指令、等了 5 秒、状态还没变 → 说明电脑没响应（可能电源线松了、主板卡了）→ 可以告警 |
| **4. 成本极低** | 一个 817D（几毛钱）+ 两个电阻 + 一根 SATA 分线器，总共不到十块钱 |

---

**所以要不要加？**

- **不加**：明天能跑通，但你是「蒙着眼睛按按钮」。想开机的时候，有可能把开着的电脑给关了。
- **加**：多花不到十块钱、多接几个元件、多调试半小时，换来「看得见」。

**我的建议：MVP 先不加（先保证明天能跑通），但把它排在阶段二的**第一项**做。** 因为它是这个项目里性价比最高的一项增强 —— 花最少的钱，解决最大的功能缺陷。

> 下面的 5.9.1 是它的电路细节。你现在**不用急着看懂**，等要做的时候再回来看。

#### 5.9.1 电路细节

> 上面 5.9.0 讲的是「**为什么**要做」，这一节讲「**怎么接**」。做二期时再回来看，现在不用急着看懂。

加第二个 817D，**反向使用** —— 不是驱动，而是**读取**：

```
╔═══════════ PC 侧 ═══════════╗         ╔═══════════ ESP32 侧 ═══════════╗
║                              ║         ║                                 ║
║  SATA 电源的 5V 线（红）      ║         ║   3V3 ──[R4 10kΩ]──┬── GPIO6    ║
║      │                       ║         ║                    │            ║
║   [R3 470Ω]                  ║         ║              817D pin4 (C)      ║
║      │                       ║         ║                    │            ║
║  817D pin1 (A) ──►|          ║         ║              817D pin3 (E)      ║
║  817D pin2 (K) ── SATA 黑线(GND)║      ║                    │            ║
║                              ║         ║                   GND           ║
╚══════════════════════════════╝         ╚═════════════════════════════════╝
              ═══════ 隔离边界 ═══════
```

**原理：**
- PC 关机时，SATA 电源的 5V 是**没有的**（只有待机 5VSB，但它不上 SATA 线）→ 光耦 LED 不亮 → 光敏三极管截止 → GPIO6 被 R4 拉到 3.3V = **读到高电平 = PC 关着**。
- PC 开机时，SATA 5V 出现 → LED 亮 → 光敏三极管导通 → GPIO6 被拉到 GND = **读到低电平 = PC 开着**。

**为什么选 SATA 5V 而不是主板 PWR_LED 排针？**
- SATA 电源线的 5V 和 GND 是**明确的、不会搞错极性的**（红线 = 5V，黑线 = GND）。
- PWR_LED 排针的正负极各家不同，而且主板已经串了限流电阻，你再加电阻可能导致亮度不足，不加又可能过流。
- 只需要一根几块钱的 SATA 电源分线器。

**成本：** 一个 817D（几毛钱）+ 两个电阻 + 一根分线器。

**收益：**
- App 能显示 PC 的**真实**开关机状态。
- 「开机」和「关机」变成**幂等**操作：已经是开着的就不再按。
- 能检测「指令发出后 PC 没响应」，触发告警或重试。
- 光耦本身还提供隔离，和输出侧一样安全。

**这是整个项目里性价比最高的一项增强。**

### 5.10 接线步骤（按顺序做，不要跳）

1. **PC 完全断电** —— 关机、拔掉电源线、按几下机箱电源键放掉残余电。
2. **确认 PWR_SW 两个脚**：万用表电阻档，一个脚对机箱金属（地）应该约 0Ω，另一个脚应该有几 kΩ 到十几 kΩ（内部上拉）。
3. **确认光耦引脚**（见 5.3 的二极管档方法）。
4. **先离线验证光耦能工作**：
   - ESP32 侧：GPIO5 → 220Ω → 光耦 1 脚，2 脚 → GND。
   - 输出侧：拿一个独立 3.3V 电源（或另一块开发板的 3V3），串一个 1kΩ 电阻 + 一个 LED，接到光耦的 4 脚（C）和 3 脚（E）。
   - 跑一段代码让 GPIO5 闪烁，看输出侧的 LED 跟着亮灭。**这一步通了，说明光耦和你的代码都对。**
5. **接主板**：光耦 4 脚（C）接 PWR_SW 的**信号脚**（那个有几 kΩ 的），3 脚（E）接**地脚**（那个 0Ω 的）。
6. **接 ESP32 独立供电**（USB 充电头，**不要**接被控 PC 的 USB 口）。
7. **第一次测试**：发一个 300ms 脉冲，听电脑有没有反应。

### 5.11 脉冲参数（这几个数字很重要）

| 参数 | 推荐值 | 理由 |
|---|---|---|
| 脉冲宽度 | **300 ms** | 足够被主板识别；远小于 4 秒强制关机阈值 |
| 最小宽度 | ≥ 100 ms | 太短可能被主板去抖逻辑滤掉 |
| 最大宽度 | ≤ 3000 ms | 超过 4 秒 = 强制断电，必须留足安全余量 |
| 两次脉冲最小间隔 | ≥ 2 秒 | 防止密集脉冲被识别为长按或特殊组合键 |
| 指令去重窗口 | 60 秒 | 同一 nonce 在此窗口内只执行一次 |

**把这些值做成可配置（存在 NVS 里），而不是硬编码。** 不同主板对按钮的响应时间略有差异，万一 300ms 不灵，你可以直接改配置而不用重新编译烧录。

### 5.12 一个技术细节：光耦不是「理想开关」

817D 的输出侧是**光敏三极管**，不是继电器触点。这意味着：

| 现象 | 说明 | 是否正常 |
|---|---|---|
| 导通时两端电压不是 0V，而是约 0.1~0.2V（饱和压降） | 三极管特性 | ✅ 正常，主板照样识别为低电平 |
| 关断时有极小漏电流（典型 <100nA） | 暗电流 | ✅ 正常，远低于主板识别阈值 |
| 用万用表量「导通电阻」会读到几百 Ω 而不是 0Ω | 三极管不是机械触点 | ✅ 正常，不要因此以为坏了 |

**但有一个方向性问题要注意：** 光敏三极管是有极性的，集电极必须比发射极电位高。**如果你把 4 脚和 3 脚接反了，光耦会「几乎不导通」**（反向工作模式增益极低）。这就是为什么 5.10 第 2 步必须先量出哪个脚是信号脚。

### 5.13 供电与接地（隔离的成败全在这里）

这是最容易翻车的一节，请逐条核对。

#### ✅ 正确做法

- ESP32 用**独立的 USB 充电头**供电（随便一个手机充电头就行，5V/1A 足够）。
- ESP32 的 GND 和 PC 的 GND **没有任何连接**。
- 唯一的跨边界连接是 817D 内部的光。

#### ❌ 三个致命的错误

| 错误 | 后果 |
|---|---|
| 从主板的 5VSB / Molex 5V 给 ESP32 供电 | **隔离完全失效**。ESP32 的地和 PC 的地通过电源线连在一起了 |
| 把 ESP32 的 GND 接到主板任何 GND 或机箱金属 | 同上 |
| 调试时用**被控的那台 PC** 的 USB 口给 ESP32 供电 | 两个问题：① 地连在一起，隔离失效；② **PC 关机后 ESP32 也断电了，你就再也开不了机了** |

> 第三条特别值得强调，因为它同时是**安全问题**和**功能问题**。很多人调试时顺手就把 ESP32 插在被控电脑上，一插上去，这套系统就既失去了隔离，又失去了「远程开机」的能力。
>
> **调试时请用另一台电脑，或者直接用充电头 + OTA/串口日志。**

### 5.14 安全提醒

**好消息：你这个方案完全不碰市电。**

主板 PWR_SW 是 3.3V 的低压逻辑信号，电流是微安级。这和 v0.1 假设的「用继电器切 220V」是完全不同的安全等级 —— 触电风险基本为零。

但仍然要注意这几点：

| 注意事项 | 说明 |
|---|---|
| **断电操作** | 接排针前，PC 关机 + 拔电源线 + 按几下电源键放电 |
| **静电（ESD）** | 摸主板前先摸一下机箱金属或水管放电。静电可以击穿主板上的芯片 |
| **不要带电插拔排针** | 待机时 PWR_SW 上有 3.3V，插拔瞬间可能产生尖峰 |
| **不要短接到其他脚** | 只短接 PWR_SW 那两个脚。碰到相邻的排针（比如 HDD_LED、RESET）可能造成意外 |
| **绝缘柄工具** | 用螺丝刀测试时，手只握绝缘柄 |
| **保修** | 自己接线可能影响主板保修，心里有数就行 |

> 如果以后你想扩展成「用继电器控制插排/大功率负载」，那就回到 v0.1 的警告：**涉及市电，没有电气安全知识和资质不要自己动手。**

## 6. 失联与故障处理

### 6.1 掉线时应该怎么办？

**这次答案很简单，因为你的执行器是「瞬时按钮」而不是「持续状态」。**

| 场景 | 处理 |
|---|---|
| MQTT 掉线 | **什么都不做**。PC 保持当前状态。这是唯一合理的选择 —— 你没有任何「持续输出」需要维持或撤销 |
| 收到指令，执行脉冲到一半掉线 | **脉冲照常完成**。脉冲是本地时序，不依赖网络 |
| 掉线期间用户发了指令 | 指令丢失（QoS 1 且会话未保持时）。App 应提示「设备离线，指令未送达」 |
| 重连后 | 重新订阅 `psw/<device_id>/cmd`，发布 status = online（retained） |

**注意：** 这和 v0.1 里「加热器掉线要不要断电」是完全不同的问题。你控制的是电脑，掉线时保持现状是**安全的**。

**但要小心一件事：掉线重连后不要「补执行」离线期间错过的指令。** 想象一下：你早上发了「按一下」，但设备离线没收到；下午设备重连，把那条指令补执行了 —— 电脑在你不知情的时候被按了一下。**必须设置会话为「不保持」（clean session）或指令 TTL 校验，确保陈旧指令被丢弃。** 这就是 4.2 里 `ts + ttl` 的价值。

### 6.2 心跳 与 LWT（Last Will and Testament，遗嘱消息）

**LWT 是什么？** 打个比方：
> 你去医院做手术前，先跟律师说：「如果我手术台上没下来，你就把这份遗嘱公布出去。」
> MQTT 的 LWT 就是这个：设备连上 broker 时，先登记一条「遗言」；如果设备异常掉线（没有正常发送 DISCONNECT），broker 就替它把这条遗言发出去。

**配置示例：**

```c
.will = {
    .topic   = "psw/<device_id>/status",
    .msg     = "{\"online\":false,\"reason\":\"lwt\"}",
    .msg_len = 0,
    .qos     = 1,
    .retain  = true,
},
.session.keepalive = 30,   // 秒
```

正常上线时，设备向同一个主题发布 `{"online":true}`（retain = true）。这样手机订阅后立刻知道设备在不在线。

**keepalive 怎么选？**
- 太小（< 15s）：网络抖动就断，重连风暴。
- 太大（> 120s）：掉线 2 分钟手机才发现。
- **推荐 30~60 秒。**

### 6.3 看门狗（Watchdog）—— 本项目里它是安全相关项

**看门狗是什么？** 一个独立的小闹钟。程序必须定期「喂狗」（告诉它我还活着）。如果程序卡死了忘了喂，闹钟就响 —— 芯片自动重启。

**先诚实地划清边界：看门狗能救什么、不能救什么。**

回忆 5.7 的故障分析：**如果 GPIO5 卡在高电平超过 4 秒，电脑会被强制关机。** 而看门狗的超时通常设 5~10 秒 —— 也就是说，**看门狗救不了这一次强制关机**，4 秒那一刻主板已经动手了。

那看门狗的价值在哪？在于**让你还能把电脑开回来**。

想一下没有看门狗的情况：程序死锁 → GPIO5 永久卡在高电平 → 电脑 4 秒后被强制关机 → 但 PWR_SW 两脚**一直处于短接状态**。这时你从手机再发「按一下」：设备是死的，收不到；就算收到了，PWR_SW 已经被持续按住，主板根本不会响应开机。**结果：你必须回家手动拔插头，远程控制彻底失效。**

有了看门狗：5~10 秒后芯片自动重启 → GPIO 回到高阻 → PWR_SW 断开 → 设备重新上线 → 你又能远程开机了。

> 一句话：**看门狗不是用来阻止「这次关机」的，是用来保证「你还有下一次机会」。**

| 类型 | 作用 | 配置 |
|---|---|---|
| **Task WDT**（任务看门狗） | 监控某个任务有没有按时喂狗 | `esp_task_wdt_init()` + `esp_task_wdt_add()` + 定期 `esp_task_wdt_reset()` |
| **Interrupt WDT**（中断看门狗） | 监控中断有没有长时间不返回 | 默认开启，保持默认配置即可 |

**关键设计：**
- 只在**主循环正常跑完一轮**时才喂狗。
- 不要在一个「什么都不做的空循环」里喂狗 —— 那是自欺欺人。
- **超时时间怎么选？** 原则只有一条：**要比「这个任务里最长的一次正常阻塞」更长**，否则正常干活也会被误杀。你的脉冲只有 300ms，正常一轮循环也就几十毫秒，所以 **5~10 秒非常宽松、非常安全**。（⚠️ 注意：这个数字和 4 秒强制关机阈值**没有关系**，别把两者搞混 —— 后者是主板的行为，前者是你的软件配置。）
- 重启后 GPIO 回到高阻 → 光耦断开 → PC 不受影响。

### 6.4 重连退避（Backoff）

**问题：** 如果 broker 抖动，你的设备每秒重连一次。虽然只有一台设备，但 EMQX Serverless 的免费额度是按「连接分钟数」计算的 —— **疯狂重连会快速消耗额度**，而且可能触发服务端的连接频率限制。

**正确做法：指数退避 + 随机抖动（jitter）。**

```
第 1 次失败：等 1s  + random(0, 0.5s)
第 2 次失败：等 2s  + random(0, 1s)
第 3 次失败：等 4s  + random(0, 2s)
第 4 次失败：等 8s  + random(0, 4s)
...
上限：60s + random(0, 30s)
连接成功后：重置回 1s
```

**为什么要加随机抖动？** 如果以后你有多个设备同时断线，它们会在同一时刻重连。加了随机数，重连时间就散开了。

ESP-IDF 的 `esp-mqtt` 自带重连机制（`reconnect_timeout_ms`），但**默认不是指数退避**，需要自己实现或在事件回调里控制重连节奏。

### 6.5 一个本项目特有的问题：指令发出后 PC 没反应

因为「按一下」是单向的，你**不知道**电脑有没有真的响应。可能的原因：

| 原因 | 判断方法 | 对策 |
|---|---|---|
| PC 电源线被拔了 / 插排开关关了 | 无法判断（没有状态回读） | 二期加状态回读 |
| 脉冲太短，主板没识别 | 改配置加长到 500ms 试试 | 脉冲宽度可配置 |
| 光耦接反了 | 拆下来按 5.3 重新验 | 接线前先离线测试 |
| 光耦坏了 | 离线测试法验证 | 备一个 817D |
| 电脑正在开机自检中 | 无法判断 | 等 30 秒再试 |

**这就是 5.9 那个状态回读光耦的价值所在。** 在二期做完之前，App 上必须有明确的提示：「设备无法确认电脑的实际状态」。

## 7. 配网与 OTA

### 7.1 首次配网方案对比

| 方案 | 原理 | 安全性 | 用户体验 | 推荐 |
|---|---|---|---|---|
| **编译期硬编码** | 直接把 SSID/密码写在代码里 | ❌ 极低（密码进 Git、进固件） | 无 | ⚠️ **仅限 MVP 本地实验**，且密码不要进 Git |
| **SmartConfig / ESP-Touch** | 手机 App 把 Wi-Fi 密码编码进 UDP 广播包，设备在混杂模式下抓包 | ⚠️ **低**。密码在空口广播，附近任何设备都能抓 | 简单 | ❌ 不推荐 |
| **BLE 配网**（`wifi_provisioning` + `esp_prov`） | 手机通过蓝牙把凭据发给设备 | ✅ 中高。支持 **PoP（一次性验证码）** | 好 | ✅ 二期推荐 |
| **AP 配网（SoftAP）** | 设备开热点，手机连上去填 Wi-Fi | ✅ 中高。热点用 WPA2 密码 + PoP | 一般 | ✅ 备选 |

**PoP 是什么？** 想象你在酒店办入住，前台给你房卡，同时要求你说出预订人姓名 —— 光有房卡不够，还得证明「你确实是预订人」。PoP 就是这个「预订人姓名」，防止有人趁你配网时抢先接管你的设备。

**通用要求（不管哪种方案）：**
- 配网成功后**立即关闭配网服务**。
- 配网窗口加**超时**（例如 5 分钟无操作自动关闭）。
- 配网过程中**不允许**执行任何按键脉冲。
- 凭据写入 **NVS**。

### 7.2 MVP 的务实选择

明天就要用，最实际的做法是：

1. **把 Wi-Fi 凭据和 MQTT 凭据放在一个 `secrets.h` 文件里**，这个文件在 `.gitignore` 里。
2. 仓库里放一个 `secrets.h.example` 作为模板。
3. 这样密码不进 Git（安全），但也不用实现配网（省时间）。

**这是 MVP 阶段明确接受的权衡。** 二期的目标才是 BLE 配网。

> ⚠️ 别忘了 5.0 节：你填的 SSID 必须是 **2.4GHz** 的那个。

### 7.3 OTA 升级

**为什么 OTA 必须签名校验？**

因为 OTA 是「远程往设备里写代码」的通道。如果这个通道没被保护：
- 攻击者劫持升级服务器 → 给你的设备刷恶意固件 → 你的电源开关变成别人家的。

| 层级 | 机制 | 说明 |
|---|---|---|
| 传输层 | HTTPS + 服务器证书校验 | 防止传输中被改 |
| 应用层 | **固件镜像签名** | 设备只接受用你的私钥签过名的固件 |
| 引导层 | **Secure Boot v2** | bootloader 在启动时验证 app 分区的签名，不通过就不启动 |

### 7.4 ⚠️ 「开了就难反悔」的权衡

| 操作 | 可逆性 | 风险 |
|---|---|---|
| 开启 Secure Boot | **不可逆**（烧 eFuse） | 一旦密钥丢失或搞错，芯片**永久变砖** |
| 开启 Flash Encryption（Release 模式） | **不可逆** | 同上 |
| Flash Encryption（Development 模式） | 可逆 | 保护强度打折，仅用于调试 |
| Anti-rollback | 不可逆 | 低版本固件永远无法再刷入，回滚救砖的路被堵死 |

**正确顺序：**

```
先用 Development 模式把整套流程跑通（包括 OTA 升级、回滚）
       ↓
备份好密钥（离线、多份、异地）
       ↓
确认流程无误后，才烧 Release 模式的 eFuse
```

**对明天的 MVP：不要开 Secure Boot，不要开 Flash Encryption。** 一旦搞错，你明天就没有设备用了。但要明确记为「已知风险」（见第 10 章）。

## 8. 局域网侧加固

### 8.1 你的路由器是 OpenWrt/LEDE —— 这是好消息

`LEDE` 是 OpenWrt 的旧名，说明你的路由器跑的是开源固件，**它天生就支持访客网络和 VLAN**，不需要换硬件。

### 8.2 网络隔离

| 措施 | 在 OpenWrt 上怎么做 | 收益 |
|---|---|---|
| **独立访客网络** | 网络 → 无线 → 添加一个访客 SSID，绑定到独立的 `guest` 接口 | 简单，效果立竿见影 |
| **AP 隔离** | 访客网络的无线设置里勾选「隔离客户端」 | 同一 Wi-Fi 下设备互相不可见 |
| **关闭 UPnP** | 服务 → UPnP → 禁用 | 防止设备自己「偷偷」开端口映射（很多 IoT 设备就是这么被暴露的） |
| **DNS 出口限制** | 防火墙 → 通信规则，限制 guest 区域只能访问 broker 域名 | 即使设备被攻破，也跳不到别的目标 |
| **MAC 绑定 / 静态 IP** | 网络 → DHCP → 静态租约 | 便于审计 |

**最低成本的建议：** 把 ESP32 放到访客网络上。这一步只需要几分钟，但它把「ESP32 被攻破」的影响范围从「整个家庭内网」缩小到「一个空网络」。

**如果嫌麻烦，至少在路由器上做这两件事：**
1. 关闭 UPnP。
2. 确认没有给 ESP32 的 IP 做任何端口映射。

### 8.3 关闭不必要的调试接口

| 接口 | 风险 | 生产环境处理 |
|---|---|---|
| **UART 日志** | 打印 Wi-Fi SSID、IP、错误堆栈 | 生产固件把 log level 设为 `NONE` 或 `ERROR` |
| **JTAG** | 可以直接读内存、改寄存器、下断点 | 用 eFuse 永久禁用（`CONFIG_ESP_EFUSE_DISABLE_JTAG`） |
| **UART 下载模式** | 通过 GPIO9 拉低进入，可重刷固件 | 配合 Secure Boot，即使刷入也无法启动 |
| **mDNS / 设备发现** | 主动广播自己的存在 | 生产环境关闭 |

**生产固件的 `sdkconfig` 建议：**

```
CONFIG_LOG_DEFAULT_LEVEL_NONE=y
CONFIG_BOOTLOADER_LOG_LEVEL_NONE=y
CONFIG_ESP_INT_WDT=y
CONFIG_ESP_TASK_WDT=y
```

> ⚠️ 调试阶段**不要**关日志 —— 你现在最需要的就是日志。这一条是「上线前」才做的。

## 10. 分阶段实施建议

### 10.1 阶段一：明天能跑通的 MVP

**目标：手机通过 EMQX Cloud，远程「按一下」电脑的电源键。**

#### 必须有

| # | 项目 | 说明 |
|---|---|---|
| 1 | Wi-Fi Station 连接 **2.4GHz** SSID | ⚠️ 别填 `LEDE-5G` |
| 2 | MQTT over TLS（8883） | **必须校验 EMQX 服务器证书**，内嵌 root CA |
| 3 | 每设备独立用户名/密码 | 32 位随机，放 `secrets.h`，不进 Git |
| 4 | Topic 结构 | `psw/<device_id>/{cmd,status,ack}` |
| 5 | **设备端 topic 逐字节校验** | 防 Serverless 无 ACL 的情况 |
| 6 | 指令 JSON + nonce + ts + ttl | 防重放；**同时防 QoS 1 重复投递** |
| 7 | SNTP 时间同步 | 同步成功前拒绝执行指令 |
| 8 | GPIO5 → 220Ω → 光耦，**R2 10kΩ 下拉** | 保证上电默认断开 |

| 10 | **脉冲在独立任务里生成**（拉高→延时→拉低） | 绝不在 MQTT 回调里直接拉 GPIO |
| 11 | Task WDT | 安全相关：防 GPIO 卡高导致强制关机 |
| 12 | 指数退避重连 | 防疯狂重连耗尽 Serverless 免费额度 |
| 13 | LWT + retained status | 手机能看到在线状态 |
| 14 | 脉冲宽度做成 NVS 可配置 | 默认 300ms，不同主板可能要调 |
| 15 | 烧录前 hash 记录 | 见第 9 章 |
| 16 | **独立供电**（USB 充电头，不接被控 PC） | 5.13 节，隔离的成败 |

| # | 项目 | 后补到 | 为什么可以等 |
|---|---|---|---|
| 1 | 状态回读光耦（5.9） | 阶段二 | 没有它系统能跑，只是「盲按」 |

### 10.2 ⚠️ MVP 阶段明确接受的风险（诚实版）

| 风险 | 具体后果 | 为什么现在接受 | 什么时候修 |
|---|---|---|---|
| **「盲按」——无法确认 PC 真实状态** | 你以为电脑关着想开机，实际它开着，结果被关机 | 状态回读需要额外硬件和调试时间 | **阶段二优先做**（成本最低、收益最高） |
| **固件未加密** | 攻击者物理接触设备 → dump flash → 拿到 Wi-Fi 和 MQTT 密码 | 明天要上线；设备在家，物理接触前提较高 | 阶段二 |
| **无 Secure Boot** | 物理接触 + 重刷固件可植入后门 | eFuse 不可逆，需先验证流程 | 阶段二 |
| **Wi-Fi 密码在固件里** | 同上 | MVP 时间约束；已用 `.gitignore` 防泄漏 | 阶段二（BLE 配网） |
| **无掉线 fail-off** | — | **本方案不存在这个问题**：执行器是瞬时按钮，掉线时保持现状是安全的 | 不适用 |
| **无独立 VLAN** | 设备与内网其他机器同网段 | topic 自校验 + EMQX 认证已限制其能力 | 阶段二 |
| **EMQX Serverless 免费额度有限** | 超额会断连 | 单设备用量很小 | 持续观察 |
| **构建机曾被入侵** | 理论上有后门风险 | 你已清理；容器构建 + hash 记录已缓解 | 持续观察 |

### 10.3 阶段二加固清单（上线后 1~2 周）

**按性价比排序：**

1. ⭐ **加第二个光耦做状态回读**（5.9）—— 成本几块钱，解决的却是本方案最大的功能缺陷。
2. ⭐ **实现幂等的「开机/关机」语义** —— 基于状态回读：已经是开着的就不按，已经是关着的也不按。
3. 划分访客网络，关闭 UPnP。
4. 实现 BLE 配网（带 PoP + 超时关闭），把 Wi-Fi 密码从固件里拿掉。
5. 实现 OTA（HTTPS + 固件签名 + anti-rollback），在 Development 模式下验证全流程。
6. 生产日志降级。
7. 建立固件 hash 台账。
8. 评估是否迁移到 EMQX 独享部署以启用 mTLS。

### 10.4 阶段三（长期）

- 如果以后要控制「插排/大功率负载」，需要继电器 —— **这时才涉及市电，回到 v0.1 的安全警告**。
- 多设备统一管理。
